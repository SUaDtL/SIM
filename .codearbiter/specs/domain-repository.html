Domain repository and validation

A typed repository that is the only write path to a SIM dataset: CRUD for every entity and link, domain validation with readable errors, IP/FQDN-like text warnings that require confirmation, derived classification, a graph snapshot for the map, and change events.

Scope

Scope

StatementTyped entities and repository CRUD for networks, organizations, categories, applications, services and CDS (with joined networks); support assignments per tier; org-consumes and service-dependency links.
SCOPE-2

Scope

StatementValidation: trimmed non-empty names up to 200 characters, valid markings and kinds, friendly duplicate-name and in-use errors, no organization parent cycles, a CDS joins at least two networks, a dependency via a CDS must connect two different networks that the CDS joins, no self or duplicate dependencies.
SCOPE-3

Scope

StatementSensitive-pattern detection for IPv4/IPv6 addresses and dotted host names in every free-text field, returned as warnings that block the write unless confirmed.
SCOPE-4

Scope

StatementDerived classification (dataset banner marking, CDS marking), a read-only graph snapshot for the map, and a change event after each successful write.

Approach

APP-1

Approach

Binding decision refs
  • DEC-1
  • DEC-2
  • DEC-3
ChoiceA Repository class over the sql.js Database with typed entity interfaces, a pure validate module (names, markings, IP/FQDN detection), domain checks inside the repository (org cycles, CDS membership, via-CDS consistency), SQLite constraint errors mapped to ValidationError, and a subscribe() change event. Only one sane approach given the coding standard that UI and importer write only through the repository.
TradeoffHand-written SQL per entity is more code than a generic table mapper but keeps each rule explicit and testable.
